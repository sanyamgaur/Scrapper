Sourced — Control Tower add-on
==============================
Drop these files into your existing sourced-full-system folder (they sit
alongside crossborder/, tests/, inventory_delhi.csv, crossborder.db). None of
your original files are changed; these only ADD a control page and endpoints.

Files:
  crossborder/console.py        new API endpoints + the /console page
  crossborder/cart.py           the Blinkit cart run + per-item cart limits
  crossborder/buysheet.py       the live buy sheet (cart adds, orders, events)
  diagnose.py                   read-only check of the database and the API
  crossborder/web/console.html  the single control-tower page
  crossborder/web/cart.html     the final link a finished cart run hands back
  crossborder/web/operator.html the buyer's sheet for a phone (/operator-run)
  run_console.py                starts everything on one port
  start-windows.bat             double-click launcher (Windows)
  start-mac-linux.command       double-click launcher (mac/Linux)

To run — Windows: double-click start-windows.bat
         mac/Linux: double-click start-mac-linux.command (or `python3 run_console.py`)
Your browser opens at http://127.0.0.1:8000/console. Do everything from there.
Close the launcher window to stop the server.

Demo path (all buttons, no terminal):
  Step 1  Run listability rules · Score stockout risk
  Step 2  Load pending clusters — Clear/Kill a cluster live
  Step 3  Prime live stock — then Open storefront and place an order,
          OR skip to step 4 and seed sample orders
  Step 4  Seed sample orders · Build batch · Build Blinkit cart ·
          Simulate operator buys · Reconcile · Pack-out bins
  Step 5  Top stockout risk · Detect restocks · Sweep price drift

Buying the batch (step 4, "Build Blinkit cart")
-----------------------------------------------
The buy sheet used to be a page of separate product links with a quantity
printed beside each. A Blinkit link cannot carry a quantity -- the cart lives in
the Blinkit session, not in the URL -- so those quantities were advisory, and
nothing said how many units of a SKU a cart would even accept.

"Build Blinkit cart" replaces that with one guided run per dark store:

  * the batch's lines are consolidated per SKU and ordered riskiest first;
  * every item carries its own cart limit -- the most units of that SKU one
    cart takes. Hover it to see every cap considered and which one bound it;
  * you add the items one at a time, in the same Blinkit tab, and each add is
    recorded against that limit. Type a quantity above it and the row flags
    immediately, before you ever reach checkout; the server re-checks the limit
    on every add, so a stale page cannot slip one through;
  * an item the batch wants more of than one cart accepts says how many cart
    passes it needs;
  * "Finish cart" hands back two links: one permalink listing every product
    added with its quantity, and the Blinkit cart itself.

The run is stored, so reloading the page mid-run keeps your progress, and the
final link keeps working after the tab is closed.

Where the limit comes from: if BLINKIT_SESSION points at a scraper session file
(the one discover.py writes), the limit is read live from Blinkit's own product
payload. Otherwise it is computed from data the system already has -- stock,
stockout risk, the Rs.15k cart-value cap and parcel weight -- and the tightest
of those wins. Live numbers are cached for six hours, computed ones for ten
minutes so the next run tries Blinkit again. Outside India the live probe is
refused and it falls back silently, which is the normal case for a US host.

The buy sheet is live
---------------------
"View buy sheet" is no longer a snapshot taken when a batch is built. It is one
row per SKU with four quantities, and it updates itself while you watch:

  in cart          a customer is holding it, not ordered yet
  ordered          they pressed Place order; not sealed into a batch yet
  batched          sealed into the buying batch
  in Blinkit cart  the operator has actually added it during a cart run

plus what is still outstanding, that SKU's cart limit, and a feed of the events
underneath, newest first. Rows flash when their numbers move. Leave the sheet
open while you work a cart run and the last column fills in as you add items.

Nothing needs changing in the storefront for this to work:

  * Place order is read straight from the orders table -- every order the sheet
    has not seen yet becomes an ORDER_PLACED event on the next refresh, whoever
    wrote the row;
  * cart adds are picked up by a request watcher that notices cart/checkout
    POSTs already flowing through the app and reads the product/quantity pairs
    out of them. It is an observer: the request is replayed to the real handler
    untouched, failures are swallowed, and SOURCED_CART_WATCH=0 leaves it out.

If you would rather be explicit than have the watcher guess, the storefront can
post its cart directly -- one call in the cart handler:

    fetch('/api/ops/buysheet/track', {method: 'POST',
      headers: {'Content-Type': 'application/json'},
      body: JSON.stringify({kind: 'CART_SNAPSHOT', ref: cartId, items: cart})});

  kind: CART_SNAPSHOT (the whole cart -- replaces what we knew about that cart),
        CART_ADD (one line; mode "absolute" sets it, "delta" moves it),
        CART_CLEAR, or ORDER_PLACED.
  ref:  the cart or session id, so one cart's changes stay one cart.

The operator sheet (/operator, /operator-run)
---------------------------------------------
/operator redirects to it, so the link already in a browser history, on a
printed slip, or in an old bookmark lands on the fixed sheet without anyone
learning a new address. To keep the original page instead, start the server
with SOURCED_OPERATOR=legacy.

"Open operator sheet" opens the buying sheet built on the cart run, laid
out for one thumb in a dark store. It is the same engine as the console's run,
so a buy made on the phone shows on the buy sheet immediately.

What it does that a tick-list cannot:

  * every line gets an outcome, not a tick -- "added N of M", "none on shelf",
    or skip. A tick loses the quantity, and the quantity is what reconcile
    allocates from;
  * the + button stops at whichever bites first, this cart's limit for that
    item or what the batch still needs, and says which. Nobody over-buys and
    nobody exceeds a cart cap;
  * every outcome is written back to the batch line through the procurement
    engine. This was the missing half: before it, an operator could work a
    whole run and reconcile would still see nothing bought and short every
    order -- only "Simulate operator buys" ever marked a line. If a line cannot
    be written back, the sheet says so rather than letting pack-out discover it;
  * a second pass plans the remainder, not the original demand again. An item
    needing 5 with a cart limit of 2 asks for 2, then 3, then 1, and drops off
    the run once it is complete;
  * the run is server-side, so a locked phone or a closed tab loses nothing --
    reopen the same link and carry on.

Finish writes the outcome of every line, including untouched ones (recorded as
not bought), so reconcile is never left waiting on a run that is over.

When something looks wrong
--------------------------
    python diagnose.py --url http://127.0.0.1:8000

Read-only, run from the folder with crossborder.db while the server is up. It
answers the questions that otherwise need a SQL prompt: whether products carry
a parsed weight (a parcel shows 0 g when they do not -- a watch or a belt has
no weight to sum), whether placed orders reached orders/order_lines, what the
buy sheet has recorded and from where, and which HTTP method this build's API
wants for reconcile and pack-out.

Two things it commonly turns up:

  * "Build batch: PB-<date> already exists" -- today's batch is already sealed.
    Not a failure: the console now carries on with the existing batch, and the
    date box is there to seal a different day's orders.
  * cart adds not reaching the sheet -- open /api/ops/buysheet/watch-log after
    changing a cart. An empty list means the storefront keeps its cart in the
    browser and posts nothing until checkout, so the /track call above is the
    way in. A row with matched_hint false is a path the watcher ignores: add a
    word from it to SOURCED_CART_PATHS (e.g. SOURCED_CART_PATHS=session/items)
    and restart.

"Prime live stock" is demo-only: it stands in for the availability engine so
checkout can succeed. In production the availability engine writes those
readings instead. Reset a demo by deleting stock_checks/orders rows, or just
keep going — every row written is real, not mocked.
