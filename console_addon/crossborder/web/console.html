How to run the demo — read me

Do the steps top to bottom

  1. Catalogue pipeline — Run listability rules, then Score stockout risk. Watch the strip split into Blocked / In review / Allowed.
  2. Compliance queue — Load pending clusters, then Clear or Kill one row and watch the Allowed/Blocked counts move.
  3. Storefront & stock — Prime live stock (turns "Live stock rows" green), then Open storefront and place an order.
  4. Fulfilment — Seed sample orders → Build batch → Build Blinkit cart (add each item, watch the per-item limit) → Simulate operator buys → Reconcile → Pack-out bins.
  5. Signals — Top stockout risk, Detect restocks, Sweep price drift.

Words you'll see

  1. Verdict — Allowed (listable) / Review (needs a human) / Blocked (never listed).
  2. Cluster — a group of SKUs sharing one shelf + one rule; one Clear/Kill moves the whole group.
  3. Prime live stock — writes a fresh stock reading so checkout can pass. demo stands in for the availability engine.
  4. Batch — one day's orders sealed for buying, split into carts per dark store.
  5. Buy sheet — live demand per SKU: in cart (held by a customer) → ordered (Place order pressed) → batched (sealed for buying) → in Blinkit cart (the operator added it). Every one of those moves shows on the sheet as it happens.
  6. Short — an order that couldn't be fully bought; reconcile fills smallest orders first.
  7. Cart limit — the most units of one SKU a single Blinkit cart will take. Unique per item: stock, stockout risk, the ₹15k cart value cap and parcel weight each bind it, and the tightest one wins. Live from Blinkit when a scraper session is configured, otherwise computed from those inputs — hover the limit to see which one bound it.
  8. Cart run — one guided pass over a cart: items in order, one Blinkit tab, each add recorded against its limit, ending in a link to everything added.
  9. Risk bucket — CRITICAL / HIGH / NORMAL likelihood a SKU goes out of stock.

Ingest catalogueLoads inventory_delhi.csv into the products table and parses every pack size to a weight. Already done — only needed after a fresh crawl.

Score stockout riskWeighs out-of-stock history, flip rate and discount depth into a CRITICAL/HIGH/NORMAL score used to order the buy sheet and filter basket add-ons.
Classify tailSends the ~9k SKUs no rule matched to the LLM in batches. Does nothing without an API key — safe to skip for the demo.

Fulfilment funnel

Orders → one daily batch → operator buys in Delhi → reconcile → per-customer parcels.
or place real ones on the storefront.

What happens: orders consolidate into carts by dark store. Build Blinkit cart turns each cart into one guided run: every item added in order, in a single Blinkit tab, with its own limit enforced as you type — and one final link at the end. Simulating buys leaves one line short on purpose, so Reconcile shows some parcels complete and one short.

Seed sample orders demoCreates N US orders (real rows) all sharing one SKU, so consolidation and shorting are visible. Or place real orders via the storefront.
Build batchSeals all un-batched orders into PB-<date>: merges duplicate SKUs, orders lines by risk × dollars, splits into carts (≤40 lines, ≤₹15k, ≤6/SKU).
Build Blinkit cartThe buying run. Consolidates the batch into one cart per dark store, computes each item's own cart limit (live from Blinkit when a scraper session is configured, otherwise from stock, risk, cart value and parcel weight), and walks you item by item — same Blinkit tab, quantity recorded per item, over-limit quantities flagged the moment you type them. Ends with the link to everything added plus the Blinkit cart link.
View buy sheetThe live demand sheet, one row per SKU: how many units are sitting in customers' carts, how many were ordered when they pressed Place order, how many are sealed into the batch, and how many the operator has actually put in a Blinkit cart. It updates itself — every cart add and every order lands on it as it happens, with a feed of those events underneath. Leave it open while you work the cart run and watch the last column fill.
Simulate operator buys demoMarks every line bought, leaving the biggest line one unit short — stands in for a person tapping through the operator sheet.
ReconcileAssigns bought units to orders, smallest first (ties: oldest). Full fill = complete; otherwise short.
Pack-out binsOne bin per customer with ship-to and parcel weight; marks each complete or short.
Open operator sheet ↗Appears after Build batch — the real mobile buy sheet you'd hand a buyer instead of simulating.

The background engines that keep the catalogue honest between crawls.

What happens: each button runs one engine and shows results inline. These normally run on a schedule; the buttons let you demo them on demand.

Top stockout riskShows the CRITICAL-bucket SKUs from the risk engine — the ones a buyer should grab first.
Detect restocksFlags out-of-stock → in-stock transitions; stable ones become relist candidates, flappy ones are held.
Sweep price driftCompares current vs quoted prices; a drop reprices quietly, a rise flags reprice, a viability-breaking rise flags delist.
